# Competitive Build-Specs — Replicating Solibri, Navisworks Clash & SYNCHRO 4D on the Web

*Prepared 2026-07-19. Deep 5-section feature-deconstruction of the top-3 replication targets from `bim-tools-landscape.md`, grounded in Sentinel's actual code (each agent read the real files). Each spec: functional backbone & logic → graphics feasibility in @thatopen/three → trust-gap protocol → web implementation blueprint (schemas + file refs) → Sentinel's unfair advantage. This is a developer build reference.*

---

## 0. Cross-cutting synthesis & build order

**Three patterns repeat across all three targets — and they ARE the strategy:**

1. **Every target is ~40–70% already built in Sentinel.** Solibri ← `ids.ts` + `model-validate.ts` + `visibility-panel.ts`; Navisworks ← `clash.ts` + `clash-panel.ts`; SYNCHRO ← `timeline-panel.ts` + `schedule.ts` + the 5D `quantities.ts`. The work is *generalizing + persisting*, not greenfield.
2. **Each becomes defensible only when its results are governed.** The moat isn't the checker/clash/simulation — it's binding results to the ISO 19650 container version + immutable audit + the state-machine gate. Solibri/Navisworks/SYNCHRO all keep their state in a **mutable file on one laptop**; Sentinel keeps it in the governed CDE.
3. **The trust-gap killer is identical everywhere: "verify against your legacy export."** Import the incumbent's report (Solibri BCF, Navisworks clash XML, P6 XER), reconcile 1:1 against Sentinel's own result on the same IFC, and persist the signed diff on the audit chain. IDS / GUID-pairs / task_code are the neutral join keys.

**🔴 One urgent finding (act now, independent of any feature work):** the clash-deconstruction agent found that `adapter/model-clash.ts::itemsFor()` **never populates `ClashItem.guid`**, so every clash signature silently degrades to `modelId:localId` — both revision-*unstable*. **Consequence: resolving a clash does NOT survive a model revision today** (the headline feature). Fix = fetch `GlobalId` in `itemsFor()` + map `modelId→container_id` at load (≈1 day; `clash.ts` core is already correct — `keyOf` prefers `guid`). See §2 Step 1.

**Recommended build order** (highest value ÷ effort first):
1. **Clash identity fix** (🔴 correctness bug, ~1 day).
2. **Server-side result persistence + status lifecycle** for clash (the moat) and **IDS check-runs + decisions** (reuse one pattern) → move both off localStorage into Supabase with the state machine.
3. **Auto-4D from the 5D classification** (SYNCHRO Step 2) — nearly free, uniquely Sentinel's, and half-built.
4. **Narrow-phase mesh clash** (three-mesh-bvh in a worker) — the clash trust unlock.
5. **The classification + ruleset layer** for Solibri-parity checking.
6. **Legacy-export reconciliation importers** (all three) — the sales weapon.
7. State-machine **gates** wiring (a check/clash/schedule precondition on WIP→Shared→Published).

Common new infra shared by all three: `OBC.Clipper` (section box), camera fit-to-box, a Web-Worker pool, and per-target Supabase migrations (`0005_clash`, `0006_checking`, `0007_schedule`) following the `0001` CDE pattern with `0004` RLS.

# 1. Solibri Model Checker + IDS → web build-spec

*Grounded in: `sentinel-core/ids.ts`, `ids-parse.ts`, `rule-engine.ts`, `adapter/model-validate.ts`, `adapter/element-properties.ts`, `setups/visibility-panel.ts`, `styles.ts`.*

### 1.1 Core functional backbone & logic
- **The Ruleset + Classification (Solibri's real moat).** A ruleset = a tree of *rule instances* (template id, parameter table, severity, enabled). The critical indirection is **Classification**: Solibri classifies components into *roles* ("External Wall", "Accessible Door") first, and rules target roles, not raw `IFCDOOR` strings — which is why one ruleset works across Revit/ArchiCAD/Tekla output. **Sentinel gap:** `IdsApplicability` is entity+predefinedType only; the classification layer is the biggest conceptual addition.
- **Geometry rules** (intersection / clearance / accessibility / space containment). Three kernels behind parameterized fronts: intersection (broad-phase AABB → narrow-phase triangle), **clearance = "generate a virtual test volume (door swing / headroom / corridor sweep), then clash it"**, space/containment (point-in-volume + boundary coverage). None needs a B-rep kernel — tessellated geometry + BVH covers it to coordination grade.
- **Property / naming / IDS validation** — already `ids.ts` (facets, cardinality, value/pattern) + `rule-engine.ts` (token-grammar naming). Gaps vs Solibri IDS: classification/material/partOf facets, enumeration/bounds, property facets *in applicability*, and an IDS authoring UI.
- **Information Takeoff (ITO)** — tabular projection of the same property extraction + group-by + colour-by-value (a visual data audit). Sentinel already has the extraction (`parseElementProperties`) and colour (`colorCategory`).
- **Check → Presentation → BCF lifecycle** — issue = (rule, offending GUIDs, severity, status, viewpoint); **decisions ("Accepted") persist across runs** — that's what makes re-checking usable. Sentinel has the skeleton (`raiseValidationIssues`: one BCF topic per failing requirement + dedup + hash-chained audit); missing: per-element granularity, an Accept/waive state, severity levels.

### 1.2 Graphics feasibility (all already proven in `visibility-panel.ts`)
Colour by compliance/severity → `OBF.Highlighter` styles + `FRAGS.MaterialDefinition` (live: `ids_pass`/`ids_fail`; add `ids_warn`/`ids_accepted`). "Grey out others" → `model.setGhostItems` (ghost the *complement* of failing set). Isolation/zoom → `OBC.Hider.isolate` + camera `fitToBox` from `model.getBoxes` (framing is the one gap). Section box → `OBC.Clipper` (new). Viewpoints → extend the existing BCF viewpoint POST with `perspective_camera` + `coloring`. Solibri's white-model/black-edge "pen" look → already shipped via `styles.ts` `PostproductionAspect` presets → offer a "Checker view" preset. **Verdict: every Solibri visualization has a proven @thatopen counterpart here except Clipper + camera-framing (both small).**

### 1.3 Trust-gap protocol
Centerpiece — **the IDS diff:** firm exports Solibri's report/BCF for an IDS run on model V; Sentinel runs the same `.ids` on the same IFC (IDS is the neutral ground; Solibri ≥9.13 checks IDS natively); parse Solibri BCF → `Set<GlobalId>` per spec; compute per-spec `both / onlySolibri / onlySentinel`; drill-down shows GlobalId + the property Sentinel read (trace from `ids.ts`). **Acceptance: 100% agreement on existence + exact-value facets** (deterministic — any diff is a bug/interpretation divergence to disposition in writing), documented tolerance on pattern/datatype edges (boolean `TRUE`/`.T.`, unit rendering). Colour the diff in 3D (both=green, onlySentinel=orange, onlySolibri=purple). Persist as a signed report in the audit chain; 30-day parallel-run, accept after N clean deliveries. Plus: client-side execution (zero geometry egress — demo with DevTools open), engine-version + ruleset-hash stamping for determinism, and pure-TS core (`ids.ts`/`rule-engine.ts` have zero OBC/DOM imports → survive viewer-library churn).

### 1.4 Web implementation blueprint
Step 1 — widen the IDS core (`ids.ts`/`ids-parse.ts`): add classification/material/partOf facets, enumeration/bounds, and property/attribute facets *in applicability*. Step 2 — **`sentinel-core/classify.ts`** (pure): `ClassificationRule{role, match[]}` → `Map<role, ModelIdMap>` + "Unclassified" bucket; IDS + geometry rules target `role:`. Step 3 — **`sentinel-core/ruleset.ts`**: a discriminated `RuleInstance` over `ids_spec | naming | clash | clearance | headroom | space_containment | takeoff` (reusing `ids.ts` and `rule-engine.ts` as the `ids_spec`/`naming` executors). Step 4 — generalize `model-validate.ts` → `model-check.ts` (keep the proven `getItemsOfCategories` + one bulk `getItemsData` pass; geometry kinds get AABB broad-phase + worker BVH narrow-phase + generated proxy volumes). Step 5 — Supabase schema: `rulesets`, `ids_documents`, `check_runs`, `check_results`, **`result_decisions`** (Solibri's "Accepted", but governed — attributed, reasoned, expirable, RLS-gated, audit-chained), `gate_policies`. Step 6 — promote the Visibility panel's IDS strip into a **Checking tab** (ruleset picker → results tree → colour/isolate/ghost/zoom → per-element or per-rule BCF; + an IDS form-editor). Step 7 — wire the gate (server refuses a state-transition if the latest run violates `gate_policies`).

### 1.5 Unfair advantage
*"Solibri tells you whether a model **was** compliant; Sentinel makes non-compliant models **unable to progress** — and can prove it forever."* IDS-as-a-hard-gate on WIP→Shared→Published (Solibri has no state machine to gate); hash-chained proof of *which revision passed which ruleset-hash on which engine-version, and who accepted which issue*; governed acceptance (waiver register, not an anonymous local checkbox); continuous checking on every revision with trend-lines; the live BCF→Revit loop; zero-install shared truth (the client's information manager, who'll never buy a Solibri seat, opens the same URL).

# 2. Navisworks Clash Detective (+ Revizto lifecycle) → web build-spec

*Grounded in: `sentinel-core/clash.ts`, `adapter/model-clash.ts`, `setups/clash-panel.ts`, `issue-panel.ts`, `visibility-panel.ts`, `db/migrations/0001`.*

**🔴 Latent defect found:** `model-clash.ts::itemsFor()` never sets `ClashItem.guid` → signatures degrade to revision-unstable `modelId:localId` → **clash resolution does not survive a model revision today.** Fix in Step 1.

### 2.1 Core functional backbone & logic
- **Clash Test definitions** (Selection A vs Selection B via saved search/selection sets, type, tolerance, rules) that re-resolve every model drop. Sentinel hard-codes one implicit test (`CLASHABLE`-regex × all models). Build: a `ClashTest` record with declarative queries over `getItemsOfCategories` + property filters, scoped by **container** (not modelId → survives revisions).
- **Detection modes** — hard (narrow-phase triangle penetration), clearance (min triangle distance < value), duplicates. Sentinel's `boxesClash` (all-3-axis `>tol`) is a decent *broad-phase* only; narrow-phase is mandatory for rotated members, pipes/ducts (cylinders in fat boxes), sloped slabs, clearance mode, and true overlap-volume. Keep `findClashes` as the candidate generator; add worker BVH narrow-phase.
- **Status lifecycle across revisions (the crown jewel)** — `New→Active→Reviewed/Approved→Resolved(auto when the pair no longer clashes)→reopen`. Approved clashes that persist do NOT resurface. Sentinel's `dedupeClashes`+`known` (localStorage) is a binary, lossy, one-way, revision-unstable version. **Exact algorithm:** signature = sorted `container:GlobalId` pair; on run N, diff `found` vs stored → transition statuses (spec'd in §2.4).
- **Grouping + results grid** — union-find on shared-GUID + spatial clustering of overlap-AABB centroids; grid/level from `IfcBuildingStorey`; one BCF topic per *group* (fixes today's top-100-topics spam).
- **Auto-viewpoint + report export** — reuse `issue-panel.ts::viewpoint()` (Z-up perspective camera w/ coordination-matrix inversion) framed on the pair; export BCF (native, already flowing to Revit) + HTML + **Navisworks-compatible XML** for round-trip trust.

### 2.2 Graphics feasibility (mostly proven in `clash-panel.ts`/`visibility-panel.ts`)
Red/green pair → two `Highlighter` styles (pattern live). Hide/dim others → `Hider.isolate` / `setGhostItems` (live). Auto-zoom → `camera.controls.fitToBox(unionBox)`. Clash-point marker → `Box3Helper` on the overlap AABB + a cross sprite (data already in `Clash.overlap`). Section box → `OBC.Clipper` (new). Viewpoint capture proven; restore = inverse of the Z-up transform. **No Clash-Detective viewer behaviour is web-infeasible; only new components are `Clipper` + the marker overlay.**

### 2.3 Trust-gap protocol
Flagship — **legacy-export reconciliation:** import the customer's Navisworks clash report (XML preferred — carries both IFC GUIDs + clash point + distance + status); normalize to unordered GUID-pair keys (= `clashSignature` with GUIDs populated); run the same test in Sentinel on the same IFC; classify **matched / Sentinel-only / Navisworks-only**; report match %, every Navisworks-only pair isolated for inspection, per-matched delta of penetration (pass if |Δ| < tessellation tolerance ~5–10 mm). **Acceptance: 0 unexplained Navisworks-only hard clashes at equal tolerance.** Persist as a CDE audit record. Plus: false-positive regression fixtures (analytically known overlaps), published chord-error bound for curved geometry, coordination-matrix alignment before clashing, worker+BVH perf benchmarks on the customer's own federation.

### 2.4 Web implementation blueprint
Step 1 (🔴 ~1 day) — populate `ClashItem.guid` in `itemsFor()` + thread `modelId→container_id`; `clash.ts` untouched. Step 2 — `sentinel-core/clash-narrow.ts` + worker: `three-mesh-bvh` `intersectsGeometry`/`bvhcast` (hard), `closestPointToGeometry` (clearance), geometry-hash+centroid (duplicate); chunk pairs across `hardwareConcurrency-1`. Step 3 — migration `0005_clash_detective.sql`: `clash_tests`, `clash_runs` (with `container_versions` jsonb = the revision binding), `clash_groups`, `clash_results` (unique `(test_id, signature)`, `first_run`/`last_seen_run`/`resolved_run`, status enum). Step 4 — `sentinel-core/clash-lifecycle.ts` (pure, unit-testable) implements the diff; every transition → hash-chained `audit_log`. Step 5 — panel upgrade: server results (drop localStorage), test manager, status dropdowns, grouping tree, per-group BCF, HTML/XML export, live BCF↔Revit round-trip. Step 6 — `clash-reconcile.ts` importer.

### 2.5 Unfair advantage
Navisworks' clash state lives in an **NWF file on a laptop** — mutable, unaudited, dead when that coordinator leaves. Sentinel: **provenance per revision** (`first_run`/`resolved_run` → "P03 of the MEP container introduced these 42 clashes; P04 cleared 39" — a per-revision burndown Navisworks structurally cannot produce); **immutable accountability** (who Approved what, when, against which revision — tamper-evident for disputes); **state-machine gating** ("a container can't be Shared with open Critical clashes against a Published container"); one live thread (clash→BCF→Revit→re-upload→re-check, no export fork); and the reconciliation proof itself becomes an ISO 19650 deliverable.

# 3. Bentley SYNCHRO 4D (+ TimeLiner) → web build-spec

*Grounded in: `setups/timeline-panel.ts` (working 4D scrubber already fusing 5D+6D), `sentinel-core/schedule.ts`, `quantities.ts` + `adapter/fragments-quantities.ts` (the 5D classification), `cost-panel.ts`, `visibility-panel.ts`, `styles.ts`.*

### 3.1 Core functional backbone & logic
- **Schedule import preserving the planner's graph** (P6 XER / P6-XML / MSP-XML): tasks keyed by immutable external IDs (`task_code`/`UID`), WBS tree, predecessor links (FS/SS/FF/SF + lag), calendars (needed to convert hour-lags→dates). Links key to the external task ID so a re-import updates dates while links survive. Sentinel's current `Task` has no deps/calendars/WBS/task-type/actuals — extend it.
- **Task↔element binding, three tiers:** (1) manual selection sets (Sentinel already holds `taskElements: Map<string, Record<string, number[]>>`), (2) rule/property auto-matching (TimeLiner "Auto-Attach Using Rules"), (3) **derivation from the 5D classification** — the highest-leverage tier and *already running*: `indexModel()` calls the same `quantityTakeoff()` the cost panel uses; the BoQ's `RateRule.match` keys + `line.model_map` ARE a classification of every element, so a 4D rule can say "task = BoQ line C.02 ∩ Level 3" and be automatically correct *and* automatically priced.
- **Date→per-element visual state** — a pure `state(element, date)` from the governing task's **type-driven appearance profile** (Construct: hidden→green-active→built; Demolish: built→red→hidden; Temporary: hidden→yellow→hidden; Maintain: tinted while active). Sentinel's `applyDate()` is already this for Construct-only; extend to the per-type state machine + **signed** cost/carbon accrual (demolition removes value).
- **Cash-flow / resource curves** synced to the slider — precompute cumulative cost/carbon per day (linear intra-task accrual = `amount × clamp((D−start)/dur)`) → S-curve strip with a playhead. Sentinel already computes the instantaneous accrual (`perElCost`/`perElCarbon`).
- **Look-ahead & progress-vs-plan** — planned (baseline) + actual/forecast dates + `pct_complete`; late = planned_finish < status_date & not complete; ghost outside the look-ahead window. Copy the baseline/Δ diff pattern from `cost-panel.ts`.

### 3.2 Graphics feasibility (mostly proven in `timeline-panel.ts`)
Appear/disappear → `Hider.isolate`/`set(false)` (live). Colour by task type → one `Highlighter` style per type (green/red/yellow — pattern proven). Ghost look-ahead → `setGhostItems` (live). "Grow" → honest v1 = opacity ramp per tick or a rising clipping plane during a level task (SYNCHRO's voxel growth is a non-goal). Time slider + Gantt with progress fill → **already live** (`renderGantt`, the range input, the play interval). Perf: precompute per-task sorted start/finish event lists and apply only deltas between ticks + one `fragments.core.update(true)`.

### 3.3 Trust-gap protocol
**Round-trip reconciliation** (reuse `cost-panel.ts` comparison-table renderer): (1) *task census* — parsed vs XER `TASK` count, dropped tasks listed with reason (milestones→diamonds, LOE excluded — never silently), (2) *date-mismatch report* — per task, XER `target_start/end` vs Sentinel dates, target 0 rows, (3) *logic check* — `TASKPRED` count vs imported edges. **Coverage banners both directions** (always visible): unlinked-tasks, orphan-elements (in the take-off, owned by no task — would pop in at t=0), double-claim (element owned by conflicting-type tasks). **Closure invariant:** at slider=finish, accrued cost MUST equal the 5D BoQ total for linked elements (true by construction — same `buildBoQ` output — assert & display it). Revision safety: links keyed on `task_code`, re-import diff carries links over by code + flags removed-task links, written to the audit trail.

### 3.4 Web implementation blueprint
Step 1 — `sentinel-core/schedule-import/`: **`xer.ts`** (tab-delimited `%T/%F/%R/%E`; consume `TASK`, `TASKPRED`, `PROJWBS`, `CALENDAR`) + **`mspdi.ts`** (MS Project XML via `DOMParser`; `.mpp` out of scope — planner exports XML). Extend `schedule.ts` `Task` (external_id, wbs, actuals, pct_complete, task_type) + `Dependency` + `Calendar`. Step 2 — Supabase: `schedules`, `tasks` (unique `(schedule_id, external_id)`), `task_deps`, **`task_links`** (keyed on `ifc_guid` — stable across revisions, `origin: manual|rule|classification`), `link_rules`. **The killer shortcut:** a `link_rules` row `kind='boq_line'` binds a task to a BoQ line key = the *same* `RateRule.match` string that prices it → `buildBoQ(...).lines.find(l=>l.code===pattern).model_map` IS the element set (already implemented in `quantities.ts`). Compose with `kind='level'`. One classification, three dimensions — 4D and 5D can't disagree. Step 3 — refactor `applyDate` into a pure `stateAt(task, D): ElState` folded into five ModelIdMaps + batch apply + the S-curve. Step 4 — wire "Import XER / MSP XML" next to the CSV input; persist via the cost-panel's fire-and-forget CDE pattern.

### 3.5 Unfair advantage
SYNCHRO's architecture is a **copy** (export → re-import → re-link; cost lives in yet another system). Sentinel's 4D is a **view over the one governed element graph**: (1) **auto-4D from the cost classification** — a QS building the BoQ is *simultaneously* linking the programme (SYNCHRO users pay a linking engineer for weeks); (2) **cost & carbon curves correct by construction** — the S-curve at t=end *equals* the BoQ total as an invariant, and carbon-over-time is a curve SYNCHRO simply doesn't have; (3) **revision-proof `ifc_guid` links + provable audit** in the same CDE that runs the state machine; (4) **4D findings enter the same BCF→Revit loop**; (5) zero-install review with 5D+6D readouts moving under the same slider — *today*.

# 4. RIB CostX / iTWO (5D) → web build-spec

*Grounded in: `sentinel-core/quantities.ts` (`RateRule`, `resolveRate`, `buildBoQ`, `line.model_map`), `adapter/fragments-quantities.ts`, `rates.json`, `setups/cost-panel.ts` (baseline/Δ), `tender-panel.ts` (bids).*

**⚠️ Second "half-built, wrong granularity" finding** (same class as the clash-GUID bug): `cost-panel.ts`'s `setBaseline()`/`renderComparison()` diffs only **aggregated lines** (`{code, qty, amount}`), so a revision Δ tells you "Walls +40k" but not *which* walls, and offsetting changes (one wall added + an equal one deleted) **net to zero and vanish**. Fix = persist the full `ElementQuantities[]` per revision, diff by **GUID** (already read as `_guid`/`GlobalId`), roll up through `resolveRate()`. Same root cause, same fix, as clash.

### 4.1 Core backbone & logic
- **Dimension Groups live-linked to workbook cells** (CostX's spine): takeoff produces a *named persistent group of measured objects carrying a quantity vector*, and workbook cells hold **live references** (`=DimGroup("Ext walls").WallArea`), not values — change the group, every total re-flows. **Sentinel already has the primitive:** `BoQLine.model_map` IS a dimension group; `RateRule.match` + `resolveRate()` IS CostX's "Model Maps." Gap: the "cell formula" is hardcoded `qty×rate` — promote `BoQLine` to a persisted `DimensionGroup` and make cells reference `dimension_group_id + measure`.
- **Rate resolution: composite AND first-principles build-ups.** A rate is a library number OR a build-up: unit rate = Σ resource lines (`qty_per_unit × resource_rate`, resources typed Labour/Plant/Material/Sub in a shared library, productivity + waste factors), + markup % rows. Sentinel's `RateRule` is composite-only; the seam is `line.rate = rule.rate` in `buildBoQ()` — add `build_up?: ResourceLine[]`; `rule.rate` becomes derived. Stays pure TS/unit-testable.
- **Method-of-measurement via templates** (NRM1/NRM2/CESMM4/POMI/UniFormat): never hardcoded — coded hierarchy + phrase libraries + per-item conventions, shipped as workbook templates; model maps target template codes. Sentinel: add `BoQTemplate {mom, nodes[{code,title,unit,parent,measurement_note}]}` (JSON packs like `rates.json`); `RateRule` gains `target_code`; `buildBoQ` rolls up into template nodes. Uncoded → visible "Unclassified" branch (never dropped).
- **Auto-revisioning (the moat):** re-import → match by GUID → added/deleted/changed sets → deltas flow to the priced estimate automatically (live-link) → colour-coded in-grid → both revisions retained. Sentinel's fix above makes this real; add a geometric/type fallback + "GUID churn detected" flag for tools that regenerate GUIDs.
- **Subcontractor bid comparison:** `tender-panel.ts` is ~80% there (scope from `buildBoQ`, per-line lowest highlight, variance). Missing: XLSX round-trip (bidders won't type in your panel) and **unpriced-item flagging** — today `b.rates[l.code] ?? l.rate` silently substitutes the estimate rate (false precision — fix immediately, flag instead of default).
- *iTWO delta (roadmap):* cost items ↔ 4D activities (cashflow curve), procurement packages from BoQ branches — one join table onto Sentinel's 4D + tender seams.

### 4.2 Graphics feasibility
Colour-by-cost heatmap (quantile bins → one `Highlighter` style per bin, cold→hot ramp — emit optional `per_element:{guid,amount}[]` from `buildBoQ`); colour-by-BoQ-line/MoM-section (categorical palette + legend chips ↔ grid rows); revision-compare colouring (`rev_added` green / `rev_changed` amber / **deleted rendered as a transparent-red ghost by keeping the OLD revision's Fragments model loaded** — uniquely possible because both revisions live in the same CDE). Workbook grid = plain-DOM `<table>` (no grid framework) + `contenteditable` cells + expandable build-up sub-rows + sticky header + a tiny formula evaluator. **2D PDF takeoff:** pdf.js → canvas, overlay click-capture, scale calibration (`m_per_px`), shoelace area / segment length / pin counts → output an `ElementQuantities`-shaped record with `model_id:"pdf:<doc>:<page>"` so `resolveRate`/`buildBoQ` **price 2D and 3D through one pipeline, zero changes to `quantities.ts`.**

### 4.3 Trust-gap protocol
Total provenance (every figure → elements on click + which Qto set/quantity/gross-vs-net produced it — extend `readQto()` to keep `{qto_set,quantity_name,net}`). **Legacy reconciliation import (first-class feature):** import CostX/Excel BoQ → staging table → map by code (or fuzzy wizard, persisted) → 3-section diff: *quantity deltas per matched item* (±2% tolerance band, unit-mismatch = error never silent-converted), *Sentinel-only lines* (isolatable in viewer), *legacy-only lines* (= the 2D-takeoff backlog). Plus an **unmeasured-elements report** (invert the `COSTABLE` filter: "214 IfcFlowSegment not in any bill" — the sentence that prevents the lethal miss). NRM2 honesty: measurement-basis badges ("IFC NetSideArea" vs "NRM2 6.5.2 openings ≤1m² not deducted") + a small pure-TS measurement-rules layer + amber banners where the model lacks data. Revision safety: deltas are **pending until accepted** (accept-all/per-line/reject-with-comment), each acceptance an audit event.

### 4.4 Blueprint (build order de-risks each step)
1. `rate-engine.ts` (pure) — `Resource`, `RateItem` (back-compat with `RateRule`), `evaluateRate()` at `buildBoQ`'s line-120 seam; build-up expander in `cost-panel.ts`. 2. `templates/nrm2.json`+`cesmm4.json` + `boq-template.ts`. 3. **Revision snapshots + GUID diff** (highest priority after 1): `element_snapshots(model_revision_id, guid, …)`, `diffRevisions()` (pure, epsilon-compared), roll up via `resolveRate` → drillable `renderComparison`. 4. Supabase: `rate_libraries`/`resources`/`rate_items`/`rate_build_up_lines`, `boq_templates`/`_nodes`, `workbooks`/`boq_items`/`dimension_groups`, `model_revisions`/`element_snapshots`/`quantity_deltas` (append-only), `legacy_boq_lines`, `pdf_takeoffs`. 5. Workbook UI + bid XLSX round-trip. 6. 2D PDF takeoff (`pdf-measure.ts` pure geometry). 7. Cost-loaded IFC (`Pset_SentinelCost` per element via web-ifc) + NRM2 XLSX export.

### 4.5 Unfair advantage
*"CostX built a brilliant bridge between the model file and the estimate file; Sentinel makes them the same governed dataset, so the bridge — and its manual toll of re-import/re-link/re-check — disappears."* Auto-revisioning is **automatic** (runs on every CDE state transition, not when a QS remembers to re-import an emailed file); cost **inherits** the audit trail (tender total → `quantity_deltas` → `model_revisions` → CDE suitability/author/timestamp) instead of asserting "based on Rev C"; **IDS gates cost-data quality upstream** (a model that would produce `missing_qto>0` fails validation before it reaches the QS); one classification drives **cost + schedule + carbon so they can't disagree** (CostX/iTWO sell that unification as an enterprise tier); deltas are live coordination objects (clickable/isolatable/→BCF), not emailed screenshots.

# 5. Ideate / DiRoots (parameter & data management) → web build-spec *(ship FREE/bundled — DiRoots proves it's a $0 layer)*

### 5.3 Trust-gap: write-back safety (the whole game)

# 6. One Click LCA (6D carbon) → web build-spec

*Grounded in: `sentinel-core/carbon.ts` (`buildCarbon`, `resolveFactor`, gap counters, `gfa` intensity), `setups/carbon-panel.ts`, the shared `quantities.ts`/`fragments-quantities.ts` classification.*

Sentinel already computes a whole-project A1–A3-implicit carbon report with hotspots, gap counters, editable factors + live recompute, per-line isolation, CSV export. Missing: EN 15978 stages, real EPDs, material-level mapping, compliance, benchmarking, carbon-back-to-BIM.

### 6.1 Core backbone & logic
- **EN 15978 stages (A1–A3, A4, A5, B1–B7, C1–C4, D):** each mapped resource carries a **stage vector**, not a scalar; A4=transport scenario, A5=install/waste, **B4=`ceil(RSP/service_life−1)×(A1A3+A4+A5+C)`**, C/D=EoL scenario, **D reported separately never summed**. So `CarbonFactor.factor:number` → `stages: Partial<Record<Stage,number>>` + `service_life_years` + scenario refs; `total_kg` = configurable **stage scope** filter ("Upfront A1–A5" and "WLC A–C" both one filter away). Keep the legacy scalar path for back-compat.
- **Model quantities → EPD mapping (the heart):** persisted `model_key → epd_id + declared_unit + unit_conversion` (EPDs declare per kg/m³/m²/piece with density — must convert model units); fuzzy suggestions + confidence; unmapped flagged. = `resolveFactor` generalized to a persisted per-project table + a 3rd tier `category:type:material` (pull `IfcMaterial` via `HasAssociations` in `fragments-quantities.ts` — the one adapter change). Honesty flag → `mapping_status: specific|generic|unmapped`.
- **EPD/factor database (why EC3 matters):** EPDs = structured openEPD docs (declared unit, density, GWP per stage, 5-yr validity, geography), **versioned** so a report reproduces byte-identically. Don't build a database — **integrate EC3's free open API.**
- **Compliance reporting (LEED/BREEAM/EPBD/CALGreen/Part Z):** a `Scheme` is data (`{required_stages, scopes, metric total|/m²|/m²/yr, thresholds, rsp}`); evaluation = filter `CarbonReport` by scope → sum stage vector → ÷gfa ÷rsp → compare; **completeness check reuses the gap counters** (unmapped/missing beyond tolerance → "INCOMPLETE," never a final-looking number).
- **Carbon back to BIM + benchmarking:** per-element results (via `model_map`) → `Pset_SentinelCarbon` overlay; benchmark = store finalized `{intensity, building_type, gfa, scope}`, render percentile (native to Supabase multi-project, not an anonymized SaaS aggregate).

### 6.2 Graphics feasibility
**Carbon heatmap** (the sales hook): after `buildCarbon`, per-element intensity → **quantile** bins (not linear — one hot core would flatten everything) → one graded `Highlighter` style per bin (green→amber→red; *load the `dataviz` skill before finalizing colours*) → `highlightByID` per bin; un-assessed = neutral grey (honesty in 3D); legend strip + click-through reusing `isolate()`. ~a day. Stage/material charts = extend the existing plain-DOM hotspot bars into stacked stage bars (D outside the bar per EN 15978) + SVG donut + a benchmark strip with regulatory-limit markers (the graphic that gets screenshotted into planning submissions). Dashboard: hero + a **stage-scope selector** (re-filters without re-takeoff — same pattern as the factor-edit `recompute()` loop).

### 6.3 Trust-gap protocol
Fear "factors right/current?" → **EC3 as source of record** + per-line provenance (EPD id/operator/validity/retrieval) + validity enforcement (past 5yr → amber + gap banner) + **pinned immutable EPD snapshot per assessment** (live library for new mappings, frozen for issued reports). Fear "match my One Click report?" → **line-by-line reconciliation harness** on 2-3 past projects: join on material, classify every delta into exactly four causes (quantity / unit-conversion / factor / scope), ±2% quantity tolerance, publish the reconciliation as an artifact; pure-math fixture test through `buildCarbon` (any residual = mapping choice not engine error). Fear "EN 15978 compliant?" → encode rules as asserted invariants (D never summed; RSP explicit; **GFA definition — the #1 intensity dispute — upgraded from the Σ-slab-area heuristic to IfcSpace/storey-based or a user override**) + generated method-statement annex + completeness gating.

### 6.4 Blueprint
1. Extend `carbon.ts` to stages (`Stage` type, `stages` vector, A4/A5/B4/C derivations, `StageScope`; keep scalar path). 2. `epd.ts` (openEPD `Epd` type) + EC3 API client **behind the bridge** (token server-side, cached to Supabase `epds` append-only by `(id,version)`); `carbon-factors.json` → seed of `factor_libraries`. 3. ### 6.5 Unfair advantage
*"One Click LCA computes a carbon number **about** a model it once saw; Sentinel computes a governed carbon record **of** the model the project is actually building."* The WLC number **inherits the ISO 19650 audit trail** (`carbon_assessments.model_revision_id` → which revision, which state, whose sign-off) — decisive once EPBD 2028/2030 + CALGreen make carbon a **permit-stage artifact** a silo can't provenance; no export hop / no staleness (the CDE knows when an assessment is against a superseded revision); **one classification → cost and carbon can't diverge** (the "€/tCO₂e saved" trade-off One Click sells as a module = a join on `line.code`); carbon-over-time on the 4D player (One Click has no timeline); and the surfaced-never-hidden gap counters ARE the EN 15978 completeness declaration.
