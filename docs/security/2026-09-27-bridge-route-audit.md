# Bridge route audit — authorization gaps (H0), 2026-09-27

The bridge is reachable from the internet through Tailscale Funnel. This audit checked every route for what four callers can do: a **stranger** (a signed-up account that belongs to no project — sign-up is open), a **viewer**, a **contributor**, and an **unauthenticated** caller. Five auditors covered the route slices of `WebApp/bridge/bcf-service.mjs`; a skeptic re-read the code for each finding and tried to refute it; a completeness critic found and audited the routes the auditors missed.

Result: **63 findings kept** (critical 4, high 21, medium 16, low 22); 1 refuted. "real" = the skeptic confirmed it; "partly" = confirmed with a smaller impact or a different actor (severity shown is the corrected one). Paths are in `WebApp/bridge/` unless marked. No secret values appear here.

The fixes are planned in `docs/superpowers/plans/2026-09-27-h0-bridge-hardening.md`.

## Root causes

1. **"Signed in" is treated as "trusted".** Sign-up is open, and any account can create a project and become its owner, so every check that only asks for a membership of *some* project lets a stranger through on their own project.
2. **Bodies are read before permissions are checked.** JSON bodies up to 256 MB and raw uploads up to 2 GB are held in memory before the route asks who is calling.
3. **Writes a viewer should not make get through where the database policy is loose** (`bridge_docs` rows: RFIs, tenders, clashes, topics, keystore), and some routes never ask for a role.
4. **A refused write still writes a ledger row.** When row-level security refuses an update or delete, PostgREST answers with zero rows, not an error; the store then writes its audit row with the service key and reports success.
5. **Some reads use the service key or the local disk with no membership check** (sheets, views, project scope, office standards through a project attached to someone else's office).
6. **Names written into records come from the request**, not from the verified sign-in, on a few routes.

### critic

Coverage: I compared every url.pathname comparison and regex in bcf-service.mjs (:595-1718) and every branch of the /cde/ segment dispatcher (:1005-1359) against the auditors' list. Every canonical route is covered, including all 12 /ai/run-tool tools (ai-tools.mjs:23-153 matches the list). The only gaps were the aliases and lookup-then-405 paths below, plus the two body-reader helpers. bcf-service.mjs is the only HTTP listener (:462). mcp-server.mjs is stdio (mcp-server.mjs:1, 231) and calls the bridge with BCF_TOKEN (:22). intake.mjs is a CLI that POSTs /cde/:key/intake with BCF_TOKEN. watch-outbox.mjs is an fs watcher. public-client/sentinel-verify.mjs is a client library.
- GET/PATCH/DELETE /bcf/3.0/projects/:pid/topics/:guid and GET/PUT/DELETE .../comments|viewpoints read the topic (cde-store.mjs:1554-1557 bcfGetTopic goes through sb(), which uses RLS under a forwarded JWT and the service key under BCF_TOKEN) and then answer 405 (bcf-service.mjs:1668-1669, 1714). No topic data is returned. The only signal is 404 versus 405 on a random v4 GUID, and with RLS armed a non-member gets 404 either way. Not exploitable.
- GET/POST /tenders/:pid/:guid (:922-923, 939) and POST/PATCH/DELETE /rfis/:pid/:guid (:836-837, 852) behave the same way: a read, then 405, with no body leaked.
- GET|POST /cde/:key/transmittals/:x and /cde/:key/audit/:x reach the same listTransmittals/createTransmittal (cde-store.mjs:1596-1609, both ensureProject, so a non-member gets 403 under forwarding) and listAudit/recordAudit calls as the canonical routes. They add no privilege, and fixes in those functions cover them.
- GET /cde/:key/snapshots/:revId/:x runs the same getRevisionSnapshots(p3) as the covered route (bcf-service.mjs:1319). That call ignores the key, so the covered finding applies to both URLs.
- GET /receipt/:key/verify with a credential falls to receiptFor(key,'verify') (bcf-service.mjs:1409-1412, cde-store.mjs:1236-1239). That is the same code as the covered GET /receipt/:key/:auditId, and a non-numeric id finds no row.
- The /health exemption checks only the path, not the method (bcf-service.mjs:584). An anonymous POST/PUT/DELETE/HEAD /health gets past the gate, but only GET /health has a handler (:595), so everything else ends at the final 404 (:1636). No other handler matches '/health'. The pathname is normalized by new URL once (:547), so the exemption and the routing see the same path.
- HEAD and unknown methods reach no handler and end at 404 after the auth gate.
- Invalid request targets such as '//' are answered 400 by the per-request error boundary (:466-479) and never crash the process. 500 messages are scrubbed in send() (:246-252).
