# Sentinel cohesion review, 2026-09-23

## 1. Verdict

He is right about the seams and mostly right about the parts. The thirty ribbon commands in four panels (SentinelAddin/App.cs:158-248) and the eleven web layouts (WebApp/src/main.ts:364-408) are built and wired, and the rehearsal proved the flagship loop live: gate pass, IDS reject, fix-in-place, accepted with a receipt (docs/testing/SIMULATION_ROOM_RUN_2026-09-22.md:10). Not all of them do what they say: ROI Dashboard fails as a project figure (RUN:62, F39), Naming Manager proposes 5 of 145 names on a stock template (RUN:92, F9, "product, major"), and every viewer-backed web panel is blocked because the platform viewer does not initialize (RUN:77, :138, F49). What is scattered is not the tools but the facts they judge by. The IDS is a per-machine file (SentinelAddin/Engine/IdsSpecFile.cs:14-15) that a bridge-wide env var silently overrides (WebApp/bridge/cde-store.mjs:784-802; IdsSpecFile.cs:8-10 says so); the ruleset resolves through a five-link file chain that ends in the pilot's embedded copy (Engine/RulesetStore.cs:36-52, 65-73) while the web bundles a second, diverged copy (WebApp/src/sentinel-core/index.ts:71; ruleset.json:3 is 1.4.1, SentinelAddin/Resources/ruleset.json:4 is 1.5.0); an office is one project key with no parent (docs/superpowers/specs/2026-09-17-office-readiness-assessment-design.md:23); the project key enters the system four ways (§3, D5). Eight rehearsal findings (F8, F13, F26, F29, F36, F43, F44, F54) are that one root cause. "Competitors are ahead" is true for defining a standard once and enforcing it everywhere (docs/UPGRADE_MAP_2026-09.md:17-20, :38) and for the review lifecycle around a verdict (docs/competitive-build-specs.md:39; UPGRADE_MAP:155); it is false for the immutable verdict, the register and the ledger, which the handoff records none of them have (docs/HANDOFF_2026-09-23.md:24-28; UPGRADE_MAP:247 "None has an immutable verdict"), and for closing the loop inside Revit with a receipt (docs/SENTINEL_ASSESSMENT_2026-09.md:41). The design answer in one sentence: finish what the Governed Intake spec already designs for the IDS (docs/superpowers/specs/2026-09-23-governed-intake-design.md:101-115), then make every standard kind a versioned, hashed artefact stored per office or project on the bridge, resolved project → office → none, pulled by Revit and stamped on every verdict, and put one "Next" strip on both surfaces that reads from those same facts.

## 5. The unifying design

This review's choice is the project spine: standards as artefacts on the project, with the office as a parent. It is the Governed Intake spec's §3 generalised, not a rival to it. The spec already designs the IDS half: a `bridge_docs` store `"ids"` doc `"active"`, `PUT/GET /cde/:key/ids`, an audit row `ids_installed`, an "Install on this project" button in docs-panel, and `resolveIdsSpec` so Governed Publish and changesets inherit the project IDS "without add-in changes" (spec 2026-09-23:101-115). Its shape:

- Office = a `projects` row; Project carries `office_key` as a DB foreign key (one migration, no new table).
- Every standard kind (ids, ruleset, naming, contract, guideline, layers, type_catalog) is an immutable `<kind>@<n>` document in the existing `bridge_docs` table plus a pointer doc holding version, sha256, actor and provenance, one audit row per version. The primitives exist: create-only `docInsert` (cde-store.mjs:989-991), `docUpsert` (:966-969), `requireMinRole` (bridge/members-store.mjs:129-134), the office-store audit idiom (office-store.mjs:113-115), and `bridge_docs` policies that accept the project uuid (db/migrations/0028_bridge_docs_project_ref.sql:1-22).
- One route family of four routes: `GET /cde/:key/artefacts` (what is in force, per kind), `GET /cde/:key/artefacts/:kind` (resolve project → office → 404, returns `{kind, version, sha256, source, body}`), `PUT /cde/:key/artefacts/:kind` (new immutable version, pointer, audit row), `GET /cde/:key/artefacts/:kind/:version` (a past version, for receipts). The spec's `/cde/:key/ids` becomes `/cde/:key/artefacts/ids`; same store, same button, one path for every later kind. Every judge reads through it: `adjudicateProposal` (cde-store.mjs:848-871), `projectNamingRuleset` (:775-782), check-registry, office-checks, changesets (changesets-store.mjs:22-36 inherits with no change, as the spec says at :111-112), MCP, and the web panels that today fall back to a bundle.
- Two amendments to the spec, stated so the spec owner can accept or refuse them. First, the resolution order at :110-111 puts `SENTINEL_IDS` first, "custody, unchanged"; this review reads that override as D3 and proposes project → office → `body.ids` → none, with the env var removed. If the spec's order stands, phase 1 does not close D3. Second, the spec lists no change to the outbox watcher (spec :184-193 names the files it modifies; watch-outbox.mjs is not among them), so Quick and Auto publish stay ungated until phase 5.
- Revit only pulls: an `ArtefactClient` with If-None-Match, and a `ProjectContext.For(doc)` that replaces the two key resolvers. Absent means "not installed for `<key>` or its office", never a shipped default (D-03, 07-decisions.md:19-24: BDS is a reference profile); the pilot's profile becomes seed data offered on the web.
- Every verdict row, receipt, Revit dialog and readiness evidence line names `kind@version · source · sha`.

Grafts from the other two proposals:

- From the Engagement Spine: the Next strip. A pure `journey-logic.mjs` over stored facts, with a step "done" only when an evidence id exists, rendered atop the dockable pane and the web project space with a "standard in force" line. Built read-only once phase 1 lands; it replaces the static Guide layout (CAPABILITY_MAP:115).
